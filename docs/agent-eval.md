# Agent 改动的统计验收

## 要解决的问题

Agent 项目最常见的退化方式不是崩溃，而是「这版好像更聪明」：换一版 prompt、加一个工具、
调低一个温度，主观上更顺眼，客观上把三条原本能过的用例弄挂了，同时修好了两条更显眼的。
没有配对比较时，这种交换会被当成进步。

目标不是做通用 benchmark，而是给**每次改动**一个可执行的验收门：

1. 同一批用例，跑基线与候选；
2. 只看两者结果不一致的配对（b / c）；
3. 用 McNemar 精确检验判断方向性差异是否超出随机波动；
4. 同时检查成本与延迟没有超预算；
5. 结论、指标、检验统计量写入哈希链台账。

## 为什么是 McNemar，而不是比较两个准确率

同一批用例上，两次运行的准确率是**配对数据**。直接比较 90% 与 93% 忽略了「哪些用例变了」：
如果变的 3 条恰好是原本就临界的用例，证据强度远低于「3 条稳定失败突然全过」。

McNemar 只看不一致对：

|              | 候选通过 | 候选失败 |
|--------------|----------|----------|
| 基线通过     | 一致     | b        |
| 基线失败     | c        | 一致     |

零假设是 b 与 c 各占一半。小样本下用精确二项检验（`2 × P(X ≤ min(b,c))`），
不依赖卡方近似。10 来条用例时，只有 6 条单向翻转（b=0, c=6）才达到 p<0.05；
这提醒我们：**小样本只能发现大效应**，不要用它证明「微小提升」。

## 三档结论

- `accept`：p < α 且 c > b，且成本/延迟未超限。
- `reject`：显著变差，或成本/延迟超限（即使准确率提升）。
- `inconclusive`：方向不显著、样本不足或 b=c。

`inconclusive` 不是「通过」。CI 里只有 `accept` 返回 0。

## 台账

每次裁决追加一行，字段包括：时间、git sha、用例集合与策略的指纹、b/c、p 值、
准确率与 Wilson 区间、成本/延迟均值、理由、上一条 hash 与本条 hash。

```bash
data-agent-eval verify-ledger eval/ledger.jsonl
```

哈希链保证「事后改一条历史结论」会被发现。它不是防篡改的密码学承诺（没有签名），
但足以防止无意的覆盖与手滑编辑。追加前会先复核现有链：若历史条目已被改写或
无法解析，`compare --ledger` 会报错并拒绝扩容（退出码 2），避免在坏链上续写。

## 怎么积累用例

1. 从真实失败里挑：线上报告的错误、用户反馈、回归 issue。
2. 每条用例必须有确定性断言（数值、工具调用、字段存在性），不要用「看起来合理」。
3. 用例集合一旦用于验收就冻结；新增用例单独跑一轮基线，避免中途换卷。
4. 需要 LLM-as-judge 时，judge 版本也纳入指纹，并接受它的噪声——这也是为什么本工具
   默认只吃 `passed` 布尔值，判定逻辑留在你的测试里。

## 局限

- 只能证明「在这批用例上更好」，不能外推到全部任务。
- 成本/延迟用配对均值；长尾延迟（P95）需要结果文件自行聚合后再写入。
- 基线本身可能过时；定期用当前主干重跑基线，否则比较的是「旧代码 vs 新代码 + 环境变化」。
